# ReCarMatch 前 500 关结构分析报告

> 数据源:仓库根目录 `levels.json`(500 关,7.9MB)。
> 所有结论均为从数据反推 + 全量回归验证,标注了命中率。未标注命中率的为分布统计。
> 分析脚本:`analyze_levels.py`;可执行校验器:`level_constraints.py`。

---

## 0. 一句话结论

前 500 关的结构规律性**远比 generator 假设的强**。棋盘是固定的三层结构,青蛙来源有一条 500/500 成立的守恒等式,连通性有一条 500/500 成立的硬约束。这些都可以直接写成生成期的约束,不需要靠"生成完丢给 AutoTest 碰运气"。

---

## 1. 棋盘是固定的三层结构(500/500)

棋盘恒为 **7 × 11**,没有一关例外。垂直方向严格分三层:

| 行 | 内容 | 命中率 |
|---|---|---|
| `y=0` | 7 个 `PayPark` 铺满 | 500/500 |
| `y=1` | 7 个 `Park` 铺满 | 500/500 |
| `y=2` | 7 个 `Empty` 铺满(通往荷花的咽喉) | 500/500 |
| `y=3..10` | 玩法区,56 格 | 500/500 |

**所有玩法元素**(`Cars`/`Entities`/`Factorys`/`Boxs`/`SubLevels`/`GridLocks`/`GridKeys`/`FreezingCars`)**无一出现在 y<3**。500/500。

> ⚠️ 坐标方向:`CellY` 越大越靠上。`Dir=Down` 表示向 y 减小的方向流动,即流向荷花区。
> 工厂 `Dir=Down` 的峰值在 y=10(顶端),这一点可以交叉验证方向语义。

**荷花槽总数 = 14**(7 Park + 7 PayPark),不是 7。判负条件 `bsl` 里的"占满"应以 14 为准。

## 2. 青蛙来源守恒等式(500/500)⭐

这是本次分析最重要的产出。

### 2.1 青蛙从哪来

**关键机制:未出现在任何实体数组里的格子,就是青蛙源格,每格产出 1 只青蛙。**

`Emptys` 数组不是"空地",它专指 y=2 那一行入口通道(437/500 关的 `Emptys` 恰好就是 7 个,全在 y=2;其余 63 关有少量额外 Empty,但 y=2 整行必为 Empty 是 500/500)。真正的"空地"是**不写进 JSON 的格子**。

### 2.2 完整等式

```
ΣTotalCarCounts
  = 未声明格数
  + len(Cars)                                  静态青蛙,每个 1 只
  + len(Boxs)                                  每个箱子恰好 1 只
  + Σ Factory.IncludeCarCount                  工厂按字段刷
  + len(FreezingCars)                          每个冰冻蛙 1 只
  + Σ (SubLevelSizeX × SubLevelSizeY + 1)      子关卡:覆盖面积 + 自身格
```

**命中 500/500,零反例。**

其中 `未声明格数 = 77 - Σ各数组条目数`。注意用**条目数**而非**不重复格子数**:`SubLevel` 的 `Floor=1`,是覆盖在 `Floor=0` 之上的第二层,可以和 `Box` 占同一格(实测 22 关、24 处如此),两条都要计入。

### 2.3 对比 DS 代码里的等式

`generator3.py` 注释里写的是:

```
ΣTotalCarCounts - 静态Cars == Σ工厂刷入 + ΣBox数 + 真正空格数
```

这条在 500 关上**只命中 3/500**。generator3 的整个配额反推逻辑(`per_candidates` 那个循环)建立在这条错误等式上,所以产出的 `TotalCarCounts` 与布局对不上。

### 2.4 顺带确认的几个数值约束

- **单色数量恒为 3 的倍数**,取值域仅 `{3, 6, 9, 12, 15}`,分布:9 占 2054 次、6 占 1037 次、12 占 217 次、3 占 40 次、15 占 3 次。
- **青蛙总量恒为 3 的倍数**,范围 6–81,均值 55。
- **颜色种类数** 2–8,主流是 7(193 关)、6(131 关)、8(117 关)。
- 颜色使用频次:Blue 501 > Red 498 > Green 496 > Yellow 494 > Purple 493 > Orange 444 > Cyan 264 > Pink 161。**颜色不是按枚举顺序取的**,Cyan/Pink 明显是高难度关才启用。

## 3. 连通性硬约束(500/500)⭐

> **从 y=2 整行出发,只穿越非 Wall 格做 BFS,所有青蛙源格必须可达。**
> 命中 500/500。

关键在于**只有 `Wall`(`Entities` 数组)是永久阻塞物**。`Box`/`Factory`/`SubLevel`/`GridLock`/`FreezingCar` 都是会被消耗掉的临时阻塞:

- 只把 Wall 当阻塞 → 全可达:**500/500**
- 把 Wall + Box 当阻塞 → 全可达:123/500
- 把 Wall + Box + Factory + SubLevel + Lock + Freeze 当阻塞 → 全可达:88/500

也就是说,设计者保证的是"**拆掉临时障碍后一定通**",而不是"一开始就通"。这条是布局合法性的底线,生成期可以 O(格子数) 校验,成本极低。

**工厂出口约束**:1572 个工厂中,出口格(`Dir` 方向相邻格)**没有一个越界、没有一个是 Wall**。1419 个指向青蛙源空格,153 个指向其他实体。

---

## 4. 工厂方向不是随机的

`generator3.py` 的 `_pick_dir()` 按全局方向分布随机采样,与工厂位置无关。真实数据里方向和位置强相关:

| Dir | 数量 | 位置特征 |
|---|---|---|
| `Down` | 1017 | 各列均匀,`CellY` 峰值在 10(顶端),向下贯穿 |
| `Left` | 246 | **CellX=6 占 98 个**(右边缘,朝内) |
| `Right` | 244 | **CellX=0 占 87 个**(左边缘,朝内) |
| `Up` | 65 | 罕见,且**从不出现在 y=10** |

规律很清楚:**工厂朝向永远指向棋盘内部的开阔方向**。边缘工厂朝内,内部工厂朝下。这是从"出口不能是墙/越界"这条约束自然导出的结果。

`Factory.IncludeCarCount` 分布:3(333)、4(328)、5(285)、6(252)、7(129)、8(89)、9(73),即**单台工厂通常刷 3–9 只**。每关工厂数 2–5 台为主(3 台 136 关、4 台 108 关、2 台 86 关)。

## 6. 其他杂项确认

- **`GridLock` 与 `GridKey` 逐色配平**:39 关全部满足锁色计数 == 钥匙色计数(39/39)。锁色只用 Red(33)和 Blue(10),每关 1 把锁为主(35 关),2 把锁 4 关。
- **`FreezingCars.FreezingLayers` 恒为 2**(171/171),`ColorType` 恒为空。
- **`SubLevel.Floor` 恒为 1**;尺寸以 3×1(46)、3×2(32)、1×3(24)、2×2(23)、2×3(18)为主。
- **`Box`/`Factory`/`SubLevel`/`FreezingCar` 的 `ColorType` 无一例外为空字符串或 null**(5695 + 1572 + 163 + 171 个实体,零例外)。有颜色的只有 `GridLock`/`GridKey`(43+43)和静态 `Cars`(42)。
- **`Box.IncludeCarCount`** 86% 为 0;非 0 时取值 2–12。结合守恒等式(每个 Box 计 1 只),`IncludeCarCount` 在 Box 上**不参与青蛙计数**,含义待确认(见重构方案第 6 节)。
- **`levels.json` 不含 `SpaceProbabilityConfigs`/`SpaceGuaranteeConfigs` 字段**(0/500),这两个配置确实全部来自独立的 `levels_probability.csv`。而该 CSV 只覆盖 48 关,**LV49–500 全部走默认表**——意味着做 501 关起**不需要配概率表**。
