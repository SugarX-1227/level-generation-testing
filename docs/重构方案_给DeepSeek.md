# A. 必须先纠正的四个认知错误

现有实现的问题不在于代码细节,而在于四个前提判断错了。不纠正这四条,重构会重复同样的路。

## A1. ❌「游戏是随机的,可解性只能靠胜率」→ ✅「颜色由状态决定,可离线推演」

**现状认知**:因为 AutoTest 跑同一关多次结果不同,推断"青蛙颜色运行时随机,生成器无法预知",于是 `generator3` 干脆不做任何可解性校验,把责任推给"多试几局"。

**这是错的。** 反编译还原的 `RandomCarManager.op()` 第一优先级是:

> 取当前已停荷花上的颜色计数,**优先选「已有 ≥2 只且还有配额」的颜色**

这是一条**确定性规则**,输入是(荷花序列状态, 剩余配额),输出是颜色。随机只在两处进入:`oo()` 的概率判定是否命中、以及前两级都落空时 `os()` 的兜底抽取。

**AutoTest 结果的方差来自测试机器人,不是关卡。** `dfu()` 选车前会 shuffle,每轮操作序列不同 → 荷花状态序列不同 → `op()` 算出的颜色不同 → 结果不同。把"机器人随机"误判成了"关卡随机"。

**重构含义**:可解性依然是一个可离线求解的搜索问题。状态 = (棋盘剩余, 荷花序列, 剩余配额),转移 = 玩家选一只可达青蛙落位 + `op()` 决定新刷青蛙的颜色。求的是"是否存在一条玩家操作序列使得全消且不判负"。而且 `op()` 是在**帮**玩家的(主动凑三消防占满),不是对抗。

> 附带提醒:反编译文档 5.4 节记载 `ConfigManager.dqv` 维护 `game_level_id → json_level_id` 映射,**显示关卡号 ≠ JSON 的 LV**。之前测的"455 关"未必是 `levels.json` 里 `LV=455` 那一关,基于它得出的 25% 胜率基线需要重新核对。

## A2. ❌ 守恒等式写错了

代码注释里的:

```
ΣTotalCarCounts - 静态Cars == Σ工厂刷入 + ΣBox数 + 真正空格数
```

在真实 500 关上**只命中 3/500**。`generator3` 的配额反推(`per_candidates` 循环)整个建立在这条错误等式上。

**正确的等式(500/500 验证通过)**:

```
ΣTotalCarCounts
  = (77 - Σ各实体数组的条目数)          ← 未声明格,每格 1 只青蛙
  + len(Cars)
  + len(Boxs)                            ← 每个箱子恰好 1 只
  + Σ Factory.IncludeCarCount
  + len(FreezingCars)
  + Σ (SubLevelSizeX × SubLevelSizeY + 1)
```

两个易错点:

1. **`Emptys` 数组不代表"空地"**。它专指 y=2 那一行入口通道。真正的空地是**不写进 JSON 的格子**,那些才是青蛙源。
2. 用**条目数**而不是**不重复格子数**。`SubLevel` 的 `Floor=1`,是叠在 `Floor=0` 之上的覆盖层,可与 `Box` 同格(实测 22 关 24 处),两条都要计入。

实现直接调用 `level_constraints.predicted_total_frogs()`,不要重写。

## A3. ❌「学习 500 关」实际只学了 4 个标量

`profile.py` 从 500 关提取的全部内容是 `ncolors` / `total` / `nfactory` / `nbox` / `fdir` 五个**边际分布**,然后各自独立采样。空间结构一格都没学。而 `generator3` 里"每 2 列插一根墙"的车道结构是凭空发明的,和真实关卡毫无关系。

更糟的是 `n_total` 采样出来后**再没被引用**,`DifficultySpec` 里 `allow_boxes` / `allow_factory` / `allow_sublevel` / `allow_gridentity` / `allow_freezing` / `max_total_frogs` 六个字段**全是死配置**,全代码库无任何读取。所以连那几个标量都没真正用上。

## A4. ❌ 可解性校验器是恒真的

`generator2` 的产物结构上不可能不可解(每色恰好 3 只、竖井布局、下方全空通道),所以 `at_solvable()` 从未拒绝过任何一关。实测:四个难度档各 50 关,**200 次调用,0 次拒绝**。

而所谓"与 AutoTest 对齐:LV1/2 步数 9/9 一致"——`simulate()` 每轮只落位一只青蛙,`steps` **恒等于青蛙总数**。LV1/LV2 各 9 只静态青蛙,所以只要能通就必然输出 9,与走棋策略正确与否无关。这不构成任何验证。

另外 `autotest_sim.py` 有三处与它自己的注释矛盾,重构时必须修掉:

| 问题 | 现状 | 应为 |
|---|---|---|
| 荷花槽总数 | `is_lose()` 硬编码 `>= 7` | 14(7 Park + 7 PayPark);且应读 `board.parking_slots`,现在该字段全程未被引用 |
| 判负谓词 | 用 `try_eliminate()`(任意3同色) | `bsl` 要求的是 `bsg`(**连续**3同色);消除用任意3,判负用连续3,是两条规则 |
| 副作用 | `is_lose()` 内部调用会改状态的 `try_eliminate()`,靠 `and` 短路才没每轮触发 | 判定函数必须纯净 |

还有一处独立 bug,可能是卡最久那个问题的直接原因:

```python
# random_car.py, oo() 概率分支
if self.rng.randrange(100) < p:      # p 来自 CSV,是 0~1 的小数
```

`randrange(100)` 返回 0–99 整数,`p=0.5` 意味着只有抽到 0 才命中,**把 50% 变成了 1%**。这解释了"用该表模拟 om() 刷蛙结果全部判负"。改成 `self.rng.random() < p` 或 `randrange(100) < p*100`。

# B. 重构指令

## B0. 目标重新定义

**产出 LV501 起的新关卡,风格与结构延续前 500 关。** 具体是:

- 主力关型是 **Factory + Box 驱动**(451–500 段:100% 含 Factory,98% 含 Box),不是静态青蛙关(全 500 关只有 5 关,占 1%,且都是 LV1–10 的教学关)。
- 静态青蛙关型可以保留,但**不应作为主产**。现有 `generator2` 覆盖的正是这 1%。

## B1. 分层架构

推倒 `generator2`/`generator3` 的双轨结构,改成四层单轨:

```
L1  布局生成器   → 产出 7×11 网格的元素放置(Wall/Factory/Box/SubLevel/Lock/Key/Freeze/青蛙源)
L2  结构校验器   → level_constraints.validate(),不通过直接丢弃重生成
L3  配额求解器   → 按守恒等式反推 TotalCarColorTypes / TotalCarCounts
L4  可解性推演   → 模拟 (玩家策略 × op() 刷色规则),判断是否存在通关路径
```

关键原则:**L2 必须在 L4 之前**。结构校验是 O(格子数) 的,可解性推演是搜索,先用便宜的过滤掉绝大多数废品。

## B2. L1 布局生成器 —— 硬性结构规范

以下全部来自 500/500 验证,不是建议:

```
棋盘恒为 7×11
y=0  : 7 个 PayPark 铺满
y=1  : 7 个 Park 铺满
y=2  : 7 个 Empty 铺满(入口咽喉)
y=3..10 : 玩法区 56 格,所有玩法元素只能出现在这里
```

⚠️ **坐标方向**:`CellY` 越大越靠上,`Dir=Down` 是向 y 减小方向流向荷花。工厂 `Dir=Down` 的峰值在 y=10(顶端)可交叉验证。

玩法区 56 格的目标构成(451–500 段实测):

```
Wall     ~14 格(25%)   范围 7–24
青蛙源    ~25 格          范围 15–34
Box      ~11 格          范围 0–21
Factory  ~3 台           范围 1–6
```

**工厂朝向必须由位置推导,不能随机采样。** 真实规律:边缘工厂朝内(`Left` 有 98/246 在 x=6,`Right` 有 87/244 在 x=0),内部工厂朝下,`Up` 罕见(65 个)且从不在 y=10。硬约束是:**出口格必须在界内且不是 Wall**(1572 个工厂零例外)。实现上先选位置,再从合法方向集里选,而不是先掷方向再放。

`Factory.IncludeCarCount` 取 3–9(占 91%)。

## B3. L2 结构校验器 —— 直接用 `level_constraints.py`

已实现,回归结果:

```
真实 levels.json            : 500 关, 通过 500, 违规 0   ← 基线,改动后必须保持
generated_factory_levels    : 20 关,  通过 0,  违规 20
```

编码的 11 条约束(C1–C11)见文件内注释。其中最关键的是:

- **C5 守恒等式**(见 A2)
- **C8 连通性**:从 y=2 整行 BFS,**只把 Wall 当阻塞**,所有青蛙源格必须可达。500/500 成立。
  注意 Box/Factory/SubLevel/Lock/Freeze 都是**会被消耗的临时阻塞**,不参与这条判定——设计者保证的是"拆掉障碍后一定通",不是"一开始就通"。数据佐证:只算 Wall 时 500/500 可达,加上 Box 后掉到 121/500。
- **C9 工厂出口**:界内且非 Wall。

**任何对生成器的改动,都必须先跑一遍 `validate_all('levels.json')` 确认仍是 500/500,再看新产出。**

## B4. L3 配额求解器

布局定完后,`ΣTotalCarCounts` 由守恒等式**唯一确定**,没有自由度。剩下的自由度只有"如何拆分到各颜色":

```
约束: 每色数量 ∈ {3, 6, 9, 12, 15}      (500 关取值域,零例外)
      Σ各色 = 守恒等式算出的总量
      颜色种类数 ∈ {6, 7, 8}            (451–500 段实测:7色21关/8色15关/6色14关)
```

颜色选取**不要用 `list(range(n))`**。真实使用频次是 Blue 501 > Red 498 > Green 496 > Yellow 494 > Purple 493 > Orange 444 > Cyan 264 > Pink 161——Cyan/Pink 明显是高难度关才启用,应按频次加权而非按枚举顺序。

如果守恒算出的总量拆不出合法组合(例如总量不是 3 的倍数),说明布局不合法,回到 L1 重生成——不要反过来去凑 `IncludeCarCount`。

## B5. L4 可解性推演 —— 这是真正的技术难点

状态定义:

```
State = (未出场青蛙源集合, 荷花序列 dvb, 各色剩余配额 ced, 已消除数)
```

单步转移:

1. 玩家选一只**可达 y=2 的**青蛙(A* 判可达,只有 Wall 是永久阻塞)
2. 该青蛙的颜色:静态 `Cars` 是预置的;Box/Factory 刷出的由 `op()` 按当前 `(荷花序列, ced)` 计算
3. `btf()` 选槽:从后往前找最近同色,插到它后面;无同色则队尾
4. `cgp()` 消除:荷花序列中**任意** 3 只同色即消
5. `bsl()` 判负:荷花序列长度 **>= 14** 且无**连续** 3 同色
6. `bsi()` 判胜:场上无青蛙且荷花序列空

搜索目标:是否存在一条玩家操作序列使得达到 `bsi`。

实现要点:

- **`op()` 必须一起模拟**,它是环境的一部分。它偏向凑三消,所以它是在缩小失败面,不是扩大。
- 随机分支(`oo()` 命中与否、`os()` 兜底抽取)的处理:先按**期望行为**(概率分支恒命中 / 恒不命中)跑两个极端,得到可解性的上下界。若两端一致就是确定结论;不一致再做采样估计。这比直接蒙特卡洛省几个数量级。
- **必须做状态记忆化**。现有 `solver.py` 的 DFS 没有 visited 集合,同构排列会指数爆炸,而且 `if res is None: return None` 会在第一次触限时直接中断整棵搜索树,把"搜索超限"当成"不可解"返回。
- A* 现在用 `list.sort()` + `pop(0)` 当优先队列,`reachable_entry()` 对 y=2 的 7 列各跑一次完整 A*(算出的最短路径 `best` 只用来判空、从不使用),`frog_at()` 又是 O(n) 全表扫描。批量生成时这是性能墙,换 `heapq` + 单次多源 BFS(从 y=2 整行反向搜一次即可得到全图可达性)。

## B6. L5 章节编排(做 501 关起特有的一层)

元素投放是**成章节的**,不是均匀铺开,直接随机采样复现不出来:

```
段        Factory   Box   SubLevel  GridLock  Freeze   色数   总量  Hard均
151-200      98%    90%       8%        0%       0%    6.7   58.9   0.58
251-300      98%    98%      64%        0%       0%    7.1   61.1   0.60   ← SubLevel 爆发
401-450      92%   100%       2%       42%      76%    6.5   51.9   0.42   ← Lock+Freeze 章节
451-500     100%    98%      22%       34%      50%    7.0   59.5   0.44
```

两个必须复现的特征:

1. **元素成簇出现**:SubLevel 在 251–300 段占 64%,到 401–450 段跌到 2%;GridLock/FreezingCar 反过来在 401–450 段集中爆发。这是人为编排的章节结构。
2. **难度有张弛,不单调**:总量在 251–400 段见顶(~61),401–450 段回落到 51.9,451–500 段回到 59.5。

501 关起的直接起点参数(承接 451–500 段):

```
颜色种类数:  6–8(7 色为主)
青蛙总量:    42–81,均值 ~59.5
HardType:    0 占 72%, 1 占 20%, 3 占 8%
Factory:     2–5 台(3 台最常见)
Box:         0–21 个,均值 ~11
SubLevel:    约 22% 的关卡包含
GridLock:    约 34%(锁与钥匙必须逐色配平,39/39 验证)
FreezingCar: 约 50%(FreezingLayers 恒为 2)
```

其他固定值:`SubLevel.Floor` 恒为 1,尺寸以 3×1 / 3×2 / 1×3 / 2×2 / 2×3 为主;`LockDoors` 在 500 关里**一次都没用过**,不要生成。

**注意 `TotalCarCounts` 与 `Emptys` 的写法**:`Box`/`Factory`/`SubLevel`/`FreezingCar` 的 `ColorType` 必须留空(5695+1572+163+171 个实体零例外);只有 `GridLock`/`GridKey` 和静态 `Cars` 带颜色。

## B7. 代码卫生(顺手要修的)

- `profile.py` **遮蔽 Python 标准库的 `profile` 模块**。换目录运行或被当包导入就会 `ImportError`。改名为 `level_profile.py`。
- `generator3._pick_dir()` 用的是全局 `random` 而非传入的 `rng`,**同一 seed 两次生成结果不同**,生成器不可复现。全部随机源必须统一走注入的 `rng`。
- `generator3` 里 `if not b: continue` 是死代码(`b` 是 Board 对象恒真);`_split_into_multiple_of_3()` 从未被调用;`diff = target - sum(per_color)` 恒为 0。
- `BoardState.copy()` 把所有障碍无条件重建为 `saw` 类型(如沿用该模式)。
- `dynamic_sim.py` 和 `generator.py` 是孤儿模块,无任何文件导入,应删除或合并。
- `test_control.py` 测的是 `solver.py`,而生产路径用的是 `autotest_sim.py`——**被验证的模块和被使用的模块不是同一个**。而且它的三个负例("绿色2只""红色5只")靠数数就能判定,不需要模拟走棋,没有判别力。

## B8. 验收标准(替换掉"AutoTest 跑 LV1-15 全胜")

| 项 | 标准 |
|---|---|
| 结构 | `level_constraints.validate()` 零违规,且 `levels.json` 回归仍为 500/500 |
| 多样性 | 生成 N 关,**唯一布局数 / N ≥ 0.95**。现状:`generated_levels.json` 50 关只有 **6 种**唯一布局,最高重复 15 次;难度1档 50 关只有 2 种 |
| 校验有效性 | 喂入人工构造的不可解关卡,校验器**必须拒绝**。现状 200 次调用 0 拒绝 |
| 风格贴合 | 玩法区构成(Wall/青蛙源/Box/Factory 格数)落在 451–500 段的实测区间内 |
| 可解性 | L4 推演给出确定结论,再由 AutoTest 实跑抽样复核 |

**"步数与 AutoTest 一致"不能作为验收项**——`steps` 恒等于青蛙数,恒真。

## C3. AutoTest 实跑复核

`drive_autotest.py` 的链路本身是通的,保留。使用时注意两点:

1. **改 `levels.json` 后必须重启 AutoTest**(`DummyLevelProvider.uc()` 的 `if (fjc) return;` 单次加载缓存),正确工作流是整批写完 → 重启 → 一次测完。
2. AutoTest 的 `dfu()` 会 shuffle,**同一关多次跑结果本来就会不同**,这是机器人的行为不是关卡的性质(见 A1)。单次跑通/跑不通都不能作为结论,必须多次取分布。

复核的正确用法是**抽样验证 L4 推演的结论**,而不是替代 L4。
